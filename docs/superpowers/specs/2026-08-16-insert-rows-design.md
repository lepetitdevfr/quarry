# Inserting Rows From the Grid — Design Spec

**Date:** 2026-08-16
**Status:** Approved, ready for implementation planning

Stage new rows in the result grid and apply them in the same transaction
as cell edits and row deletions. A staged row sits below the real rows,
its untouched cells take the database's defaults, and the generated
primary key comes back to the grid. Enum and boolean cells get a
selector rather than a free-text input, on new rows and existing ones
alike.

This is the last of the "row editing extras" in `docs/BACKLOG.md`, and
the only one that needed real design work. It builds on
`specs/2026-08-16-inline-row-editing-design.md`, which established row
identity, the generated `WHERE`, the transaction and the guard gate, and
on `plans/2026-08-16-delete-rows.md`, which reused all of it whole.

---

## 1. Motivation

Update and delete both start from a row that already exists: Postgres
told us its identity, and the primary key writes the `WHERE`. Insert has
no such row. It has to answer three questions the other two never asked
— which columns *must* be supplied, which ones the database will fill
in by itself, and what the generated key turned out to be — and each of
those answers lives in catalog metadata the current code does not fetch.

That is why this stage gets a spec rather than a plan with the design
folded in, as the delete stage deliberately did.

## 2. Catalog widening

`lookup_table` in `schema/introspect.rs` gains four attributes per
column:

```sql
a.attnotnull,
a.atthasdef,
a.attidentity,   -- '' none, 'a' GENERATED ALWAYS, 'd' BY DEFAULT
a.attgenerated   -- '' none, 's' STORED generated column
```

`TableFacts.columns` is `Vec<(i16, String, bool)>` today. Seven fields
in a tuple is unreadable, so it becomes a named struct:

```rust
pub struct TableColumn {
    pub attnum: i16,
    pub name: String,
    pub is_pk: bool,
    pub not_null: bool,
    pub has_default: bool,
    pub identity: Identity,   // None | Always | ByDefault
    pub generated: bool,      // a STORED generated column
}
```

A tuple's fields are positional, so `facts.columns[0].2` means nothing
at a glance and a field swap compiles silently — the same class of bug
the backlog's `tab_from_row` entry is about. `Identity` is a
three-variant enum rather than a `char` so matches are exhaustive: add a
variant later and every match site fails to compile until it is handled.

## 3. Insert rules — grid level

Evaluated in order. Each failing rule carries the exact sentence shown
to the user, matching §3 of the editing spec.

| # | Condition | Reason shown |
|---|---|---|
| 1 | The result is not editable at all | the existing reason, verbatim |
| 2 | A required column is missing from the result | "add `email` to the query to insert rows — it is NOT NULL with no default" |
| 3 | A required column appears twice in the result | "`email` appears twice in the result" |

**Required** means `not_null && !has_default && identity == None &&
!generated`. Nothing else can make an `INSERT` fail for a reason that is
knowable before the user types.

**Rule 1 reuses editability whole.** Insert needs one ordinary table
with its primary key present in the result, exactly as update and delete
do. The key is not needed to write the row — it is needed to display the
generated value, and to leave behind a row that can be edited or deleted
the moment it appears. A result that cannot host the key has nowhere to
put it.

This is a refusal before the typing rather than an error after Confirm.
That distinction is the same one §4 of the editing spec draws about
casts: a value the type cannot parse (`"abc"` into an integer) is only
knowable at the server, so it fails there; a missing NOT NULL column is
a static fact about the query, so it is answered up front.

## 4. Insert rules — column level

Each result column carries an insert verdict beside its existing edit
verdict.

| Condition | Insert verdict |
|---|---|
| `table_oid` is `None` | no — "computed value" |
| Its attnum appears in two result columns | no — "this column appears twice in the result" |
| `identity == Always`, or a stored generated column | no — "generated by the database" |
| Primary key **with** a default or identity | no — "generated by the database" |
| Primary key **without** either | **yes** |
| Otherwise | yes |

`GENERATED ALWAYS` is not a preference: Postgres rejects a supplied
value outright unless the statement says `OVERRIDING SYSTEM VALUE`, and
a stored generated column cannot be written at all.

A **serial or identity primary key stays read-only** because typing one
invites a collision and leaves the sequence behind the table. A
**natural primary key with no default is editable**, because otherwise
insert is impossible on junction tables, country-code tables and every
other table keyed by something a human chooses. This is the one place
where insert diverges from the "primary keys are read-only" rule in the
editing spec, and it diverges because on a new row there is no original
value to preserve.

`EditInfo` gains `insertable: bool` and `insert_reason: Option<String>`;
`ColumnEdit` gains `insertable: bool` and `insert_reason:
Option<String>`. As with editability, the frontend computes none of it.

## 5. Untouched, NULL, and value

Three states per cell on a staged row. The difference between the first
two is what the generated column list is *for*:

- **Untouched** — the column is left out of the `INSERT` column list
  entirely, so Postgres applies its default, or `NULL` where there is
  none. Renders as a dimmed placeholder: `default`, or `NULL` when the
  column has no default.
- **Explicit `NULL`** — `⌘⌫`, the gesture that already exists on
  existing rows. The column appears in the list bound to `None`.
- **A value** — typed text, bound and double-cast exactly as an update's
  `SET` value is.

Committing an **empty** input returns the cell to untouched. That is
what makes "I typed a `created_at`, now give me `now()` back" possible
without inventing another chord.

**Accepted limitation:** an empty string therefore cannot be inserted
into a text column from the grid — `''` and untouched are the same
gesture. Rare enough to be worth the simplicity, and the workaround is
one hand-written `INSERT`. Backlog.

## 6. Selectors for enum and boolean columns

Applies to existing rows as well as staged ones.

`tokio_postgres::types::Kind` already carries the values: an enum
column's `Type` is `Kind::Enum(Vec<String>)`, populated by the driver
from `pg_enum` when it resolves the type during `prepare`.
`Kind::Domain(inner)` recurses, so a domain over an enum behaves the
same. This is the same source of truth as `table_oid` and `cast_type` —
no new catalog query, no parsing.

`ColumnEdit` gains one field:

```rust
/// Fixed set of values this column accepts, if it has one. The grid
/// shows a select instead of a text input. `None` means free text.
pub choices: Option<Vec<String>>,
```

- an enum column → its labels in declaration order, which is Postgres's
  own sort order for the type, not alphabetical
- `bool` → `["true", "false"]`
- everything else → `None`

**The SQL path does not change.** The value still binds as text and
double-casts: `$1::text::"public"."mood"` and
`$1::text::"pg_catalog"."bool"` already work. A selector constrains what
can be typed, not what can be sent, so the server remains the validator
and the client still reimplements none of it.

In the grid, a cell with `choices` opens a `<select>` rather than a text
input. Native `<select>` brings type-ahead, Enter-commits and
Esc-cancels for free. `NULL` appears as an option on a nullable column,
and `⌘⌫` keeps working as the keyboard path. On a staged row, `default`
is the leading option and the state an untouched cell sits in.

Deliberately excluded: value suggestions for foreign-key columns (a
lookup against another table — a real feature, not a field), and
`check (x in (…))` constraints, which would need constraint-expression
parsing, the thing this whole design refuses to do.

## 7. Generated SQL

```sql
insert into "public"."users" ("email", "name")
values ($1::text::"pg_catalog"."text", $2::text::"pg_catalog"."text")
returning "id", "email", "name"
```

The column list holds only the cells the user touched, which is what
lets untouched columns take their defaults.

`RETURNING` names every result column that maps to a real table column,
in result order. So the generated key, every applied default, and any
`BEFORE INSERT` trigger rewrite all reach the grid as what the database
actually stored — the same truth-not-input property updates have had
since the editing stage.

A row with nothing staged generates:

```sql
insert into "public"."users" default values returning "id", "email", "name"
```

which is legal Postgres and the right statement for a table that is all
defaults.

```rust
/// One row to insert. `cells` holds only the columns the user touched;
/// anything absent is left out of the statement so the database applies
/// its default.
#[derive(Debug, Clone, Deserialize)]
pub struct RowInsert {
    /// Which staged row this is, so the reply can be matched to it.
    /// Not a grid index: the row is not in the grid yet.
    pub row: usize,
    pub cells: Vec<CellEdit>,
}

pub fn build_inserts(info: &EditInfo, inserts: &[RowInsert]) -> Result<Vec<Statement>, AppError>;
```

`build_inserts` shares `source_table` with `build_updates` and
`build_deletes`, so a non-editable result has one refusal
implementation, not three.

## 8. Apply

Batch order: **updates → deletes → inserts.**

Inserts run after deletes so that deleting a row keyed `FR` and adding a
new `FR` in one batch does not collide on the unique key. Updates run
first because that is the order already shipped, and a stable order
keeps the View SQL panel's output stable.

`run_one` is unchanged. An `INSERT ... RETURNING` reports exactly one
row, so the rowcount assert stays one implementation across all three
statement kinds — the same reason the delete stage gave its statements a
`RETURNING` they did not display. Any failure still rolls the whole
batch back, including statements that had already succeeded.

One shipped shape changes: `AppliedRow.deleted: bool` becomes
`AppliedRow.kind: StatementKind` (`update` | `delete` | `insert`). Two
booleans would make `deleted && inserted` representable, and the enum
already exists on `Statement`.

`Statement.row` keeps meaning "grid row index" for updates and deletes,
and means "index into the staged insert list" for inserts. Documented on
the field, because the frontend reads it both ways.

Guard interaction is unchanged: `plan_apply` calls `guard::decide` on
the generated statements before anything runs, and a locked connection
is refused with the guard's own denial regardless of what the frontend
believes.

## 9. Frontend

### Pure module

`src/lib/pendingEdits.ts` gains staged inserts beside the existing
`Pending` map and `PendingDeletes` set:

```ts
/** One staged new row. `cells` holds only the columns the user touched:
 *  absent means untouched (the column is left out of the INSERT, so the
 *  database applies its default). `null` is an explicit SQL NULL. */
export type PendingInsert = { id: number; cells: Map<number, string | null> };
export type PendingInserts = PendingInsert[];

export function addInsert(inserts: PendingInserts): PendingInserts;
export function removeInsert(inserts: PendingInserts, id: number): PendingInserts;
/** Committing an empty string returns the cell to untouched (§5). */
export function setInsertCell(
  inserts: PendingInserts, id: number, column: number, value: string | null,
): PendingInserts;
export function toRowInserts(inserts: PendingInserts): RowInsert[];
```

`id` is a monotonic counter, never an array index: a staged row must
keep its identity when an earlier staged row is discarded.

`totalPending` becomes `pending.size + deletes.size + inserts.length`.
`applyPatches` switches on `AppliedRow.kind` — patch, drop, or append.

### The unknown cell

An appended row has no value for a computed column: `RETURNING` can only
name real table columns, and this design never parses the user's SQL to
rediscover what `upper(name)` meant. `types.ts` gains a sentinel:

```ts
/** No value exists for this cell yet — a computed column on a row that
 *  was just inserted. Distinct from null, which is a real SQL NULL. */
export const UNKNOWN = Symbol("unknown");
```

Rendered as a dimmed `—` with the tooltip "re-run the query to compute
this". Two existing paths must handle it deliberately rather than by
accident: **copy and export** emit an empty field for it, and **sort**
places it last. Both get a test. This is exactly the kind of value that
otherwise reaches a `String()` call and ships `Symbol(unknown)` into a
user's CSV.

The alternative — re-running the query after any batch containing an
insert — was rejected. It shows computed columns correctly, but the
re-run can legitimately disagree with itself: `now()`, `random()`, a
`limit`, or a `where` the new row does not satisfy. An insert that
succeeds and then vanishes from the grid reads as a failure, which is
the worst confusion available on a write path.

### Grid and toolbar

- `GridToolbar` gains `Insert row`, disabled with `insert_reason` as its
  tooltip when the result is not insertable — the same
  disabled-not-absent shape the delete button uses, so the affordance
  stays discoverable and explains itself.
- `⇧⌘N` stages a row. `⇧⌘⌫` on a staged row discards it, with no server
  round-trip, because it never existed.
- Staged rows render after the last real row with an `.inserting` class,
  outside the sort order — they are not in the database, so there is
  nothing to sort them by.
- Cell states on a staged row: untouched → dimmed `default` (or `NULL`
  where the column has no default); explicit NULL → the existing NULL
  rendering; a value → normal; not insertable → dimmed `generated`, not
  editable.
- `App.css` uses the existing `:root` tokens. No new variable names.
- `App.tsx` holds `inserts` beside `pending` and `deletes`, clears all
  three wherever it clears `pending` today, and passes all three to
  `previewEdits` and `applyRowEdits`.

Existing keybindings this must not collide with: `⌘↵`, `⇧⌘↵`, `⌘⌫`,
`⇧⌘⌫`, `⌘S`, `⌘W`, `⇧⌘W`. `menu.rs` claims only `CmdOrCtrl+W` and
`Shift+CmdOrCtrl+W`, so `⇧⌘N` is free.

## 10. Testing

**Pure Rust.** One test per row of both rule tables in §3 and §4:
required column missing; required column present but duplicated;
identity `ALWAYS`; identity `BY DEFAULT`; a stored generated column; a
natural primary key insertable; a serial primary key not; a computed
column beside real ones. For §6: enum labels in declaration order, `bool`
choices, domain-over-enum recursion, `None` for an ordinary type.

In `sql.rs`: the column list holds only touched cells; untouched columns
are absent; an explicit `NULL` binds as `None`; nothing staged produces
`default values`; identifier quoting with an embedded `"`; cast spelling
for an enum and for an array.

**Against a real Postgres** (testcontainers, Docker must be running):

- a generated serial key comes back through `RETURNING`
- a `BEFORE INSERT` trigger's rewrite comes back
- an untouched column takes its default, while an explicit `NULL`
  overrides one
- a NOT NULL violation rolls back **an accompanying update in the same
  batch**
- deleting a natural key and inserting the same key succeeds in one
  batch — this is the ordering decision of §8, and it fails if the order
  is wrong
- a locked connection refuses at the command, with the guard's own
  denial

**TypeScript.** `pendingEdits` under Vitest: add; remove by id, not
index; an empty commit returning a cell to untouched; `totalPending`;
`applyPatches` appending, patching and dropping in one batch.

**Mutation evidence required**, reported verbatim, on three: the batch
ordering (reverse it and watch the delete-then-insert test fail), the
rowcount assert for inserts, and the guard refusal. All three have the
shape that passes with the code under them deleted — the shape this
project has already found four times.

## 12. Out of scope

- **Multi-row `INSERT ... VALUES (…), (…)`.** One round-trip instead of
  N, but the rowcount assert would become "exactly N" and fork the one
  shared implementation, a constraint violation could not be attributed
  to a row, and every row would have to supply the same column list —
  so one row taking a default and another supplying it could not
  coexist.
- **Inserting an empty string into a text column** (§5).
- **A modal insert form** for wide tables. Honestly easier to fill than
  a horizontally scrolled grid row, but it is a second editing surface
  with its own staging and validation. Revisit if filling rows in the
  grid turns out to hurt.
- **Foreign-key value suggestions and `CHECK` constraint choices** (§6).
- **Inserting into views**, unchanged from rule 4 of the editing spec.
- **Editing primary keys of existing rows**, and **optimistic
  concurrency**, both unchanged from the editing spec.
